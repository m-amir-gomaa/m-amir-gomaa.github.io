## Start with behavior

Open a project's usage guide and its live or completed example. Identify the intended action, what should persist, the expected failure behavior and the current limits. A polished cover illustration is not a running backend.

## Follow the implementation

Read the technical overview, then the specific architecture/editor/connections manual. Imported documents link an exact committed source revision. A local documentation edition is marked when it includes uncommitted documentation changes; the link then identifies the committed baseline.

## Interpret evidence precisely

- Static checks establish particular code/build properties.
- Unit tests can substitute model, network or authentication boundaries.
- Database tests establish behavior on an actual disposable database.
- Browser journeys exercise visible flows and selected failure cases.
- Hosted checks establish observed behavior at a real deployment at that time.
- A real model call is separate from a difficult-document/audio benchmark.
- Mock payment tests do not establish seller approval, real delivery or payout.

Read release dates and the current project status together. An older release can truthfully say that a feature was still future work even when a later release has shipped it.

## Prepare for the code audit

Choose one project and feature collection at a time. Trace a representative request from interface through validation, processing/storage and error recovery. Review the corresponding tests and reproduce the meaningful checks before changing behavior. Never put real customer documents, recovery keys or credentials into screenshots or public issues.

A personalized learning list and Upwork proposal/interview workflow are follow-up work; the existence of this manual is not evidence that either has already been completed.
