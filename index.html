01 / WEB & DESKTOPTypeScript · Next.js · Drizzle · PostgreSQL

Noteweld — a connected writing workspace

Write Markdown with Vim keys, connect notes, recover earlier edits and keep PDF/transcript sources beside your work. A separate desktop client uses real Neovim and local files.

Try the editor ↗Explore connections ↗Open private workspace ↗Architecture & implementation →Latest engineering update →Build history →
The engineering behind it +

The problem

Notes, source documents and local files need stable identities, clear ownership and recovery when edits or transfers fail.

What I built

  • React/TypeScript and Next.js with CodeMirror Markdown/Vim editing, saved history, wiki links, backlinks, graph navigation, keyboard search and capture.
  • Drizzle/PostgreSQL transactions, account isolation, revision checks and conflict-preserving local-folder synchronization.
  • An Electron client with a sandboxed renderer, SQLite, native PTY and actual Neovim, plus reviewed source-bundle imports.
  • Latest source work adds a shared interactive graph, PDF.js reading, reviewed Anki text exports, streaming attachment E2EE and resumable transfers up to 512 MiB.
  • Shared web/desktop processing controls for Pageweft and Sonaweft, selected-note assistant actions, explicit approvals and recoverable receipts.
  • Atomic prepaid-credit reservations and metered storage in source; checkout and hosted model inference remain disabled.

What I checked

Real PostgreSQL isolation, races, rollback and independent backup restoration; authenticated browser editing/recovery and local native Linux editor/PDF/graph/import journeys. New cryptography, transfers and service boundaries have targeted database, fixture and native acceptance checks.

Current boundaries

The hosted preview and newest local source are separate checkpoints. Final integrated web deployment, current macOS/Flatpak packages and paid-provider qualification are still in progress. Attachment E2EE covers managed file contents, not note text or all metadata. The latest engineering update lists providers and these release boundaries.

03 / MEDIA PROCESSINGPython · FastAPI · SQLite · Whisper

Sonaweft — audio to source-linked notes

Listen to timestamped transcripts, retain separate corrections and export source-linked Markdown and subtitles. Optional evidence discussion keeps citations separate from recognition.

Open live workbench ↗Architecture & implementation →Hear completed example ↗Latest integrations & providers →Build history →Review recovery & evidence →Selected code & source access →
The engineering behind it +

The problem

Transcription needs reliable processing, traceability to the recording and a clear boundary between original recognition, human corrections and generated claims.

What I built

  • FastAPI web service and CPU CLI with bounded faster-whisper processing on Modal, timestamped listening and complete portable exports.
  • SQLite job and credit transactions, quote/reserve/settle/release, retry and cancellation recovery, session-owned assets and encrypted financial snapshots.
  • Correction/speaker-label history with conflict-safe restore, hashes and stable source-segment references.
  • Scoped service grants, an independent MCP tool set and Noteweld-compatible export/import contracts.
  • A separate bounded Gemini evidence-chat implementation with cited transcript passages, explicit approval and durable usage receipts; paid inference stays off.
  • Cloudflare access, verified email/recovery, optional identity providers, Sentry monitoring and a disabled Paymob checkout integration.

What I checked

Actual CPU/cloud recognition and browser upload/correction/export; SQLite accounting, recovery, scoped APIs and evidence-chat provider/browser fixtures. The current connected-service source passed CI and is deployed. Viewing the credited NOAA example starts no new inference.

Current boundaries

English uploads up to 64 MiB / 60 minutes. No automatic speaker diarization or guaranteed factual verdicts. Paid inference, real payment delivery and private Manufact payload handling require separate qualification; checkout stays closed.

  • Scoped service grants and an independent MCP tool set for quote, approval, processing, status, cancellation and reviewed export handoff.
  • Cloudflare HTTPS, email/account recovery, Sentry diagnostics, encrypted restore-checked financial backups and disabled Paymob checkout.

05 / BACKEND APINestJS · TypeScript · Prisma · PostgreSQL

Carrier Relay — reliable freight APIs

A focused backend project for concurrent freight quotes, race-safe booking and carrier webhook retries. Three simulated adapters make failures reproducible.

Code & quickstart ↗Architecture & engineering journal →
The engineering behind it +

The problem

Carriers respond slowly, booking requests race and webhooks arrive more than once. Each failure needs a predictable database outcome.

What I built

  • Strict TypeScript/NestJS routes, class-validator payloads, JWT-protected management routes and Swagger/OpenAPI at /docs.
  • Concurrent quote fan-out with Promise.allSettled and per-adapter timeouts, retaining successful rates when one carrier fails.
  • Prisma/PostgreSQL interactive transactions with version/status predicates to prevent two requests booking one shipment.
  • Raw-body HMAC-SHA256 verification and database-unique event keys, keeping webhook recording and shipment transitions atomic.
  • Structured request/correlation logs, safe exception responses and a local PostgreSQL/Redis Docker Compose profile.

What I checked

Thirty tests pass locally and in GitHub CI: sixteen unit and fourteen real PostgreSQL/Supertest cases, including partial carrier failure, simultaneous booking and eight concurrent webhook replays. Migrations, strict typechecking and the production build pass.

Scope

A personal engineering demonstration with simulated carriers. It does not claim live carrier credentials, freight customers or a deployed commercial service. The repository contains the reproducible test and setup instructions.
